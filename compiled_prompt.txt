### 1. Allowing Variant / Dynamic Step Sizes

Allowing the agent to choose its own step size is viable. In classic optimization (e.g., adaptive gradient methods or $(1 + 1)$-evolution strategies), step size scales with uncertainty: **take larger exploratory steps when loss is flat or far from the objective, and contract step sizes when honing in on a minimum.**

#### How Step Size Was Hardcoded vs. Dynamic

In the TOTR formulation:


$$W = (A \cdot B^T) \cdot \gamma^2$$

* **$\gamma$ (gamma)** is your **global scale/step-size factor**.
* **Vectors $A$ and $B$** represent the **directional unit vectors** (eigen-directions).
* **$\Delta A, \Delta B$** represent the **perturbation radius**.

The previous prompts forced a rigid bracket (e.g., *"keep gamma between 0.05 and 0.40"*). When the model picked $\gamma = 0.35$ with vectors near $80$, the effective weights scaled quadratically to $\sim 800$, causing the forward pass to blow up into millions on a linear output layer.

#### Giving the Agent Control Over Step Sizes

Expose a dedicated parameter called `step_scale` (or `exploration_radius`), allowing the agent to evaluate the rolling journal and choose its step size:

```python
# In orchestrators/loop_optimizer.py -> activity_llm_synthesize prompt:
prompt = f"""You are an adaptive black-box parameter optimizer.
Previous Evaluations (Rolling History):
{history_table}

Current Best Loss: {payload['loss']:.4f} (Max Residual: {payload['max_residual']:.4f})

ADAPTIVE STEP CONTROL:
1. Choose an exploration regime based on the loss trajectory:
   - Coarse Step (Loss > 1.0 or plateaued): Set gamma in [0.08, 0.15], vector updates +/- 10-20.
   - Fine Step (Loss dropping or < 0.6): Set gamma in [0.01, 0.05], vector updates +/- 2-5.
2. Maintain stability: Do not choose gamma > 0.15 or vector entries > 40, as Layer 2 linear activations will explode.

Emit strictly a JSON object:
{
  "exploration_regime": "coarse" | "fine",
  "l1_w": "<totr_string>",
  "l2_w": "<totr_string>",
  "l1_b": "<floats>",
  "l2_b": "<floats>"
}
"""

```

### 3. Summary

* **Adaptive Step Sizing:** You can make step sizes variable by allowing the agent to tune $\gamma$ (global scale) and $\Delta$ (vector integer delta) based on whether the loss trajectory is flattening or descending. Keep a hard ceiling on $\gamma \le 0.15$ in C++ to prevent linear layer explosion.
* **Token Efficiency:** The low-rank TOTR vectors performed as expected (~55 tokens). The cost accumulated because Azure Functions Agents re-evaluates the static system prompt and tool definitions on every round trip of the loop. Using direct structured completion inside a single Durable Function activity bypasses those tool schemas, reducing per-iteration costs to ~250 tokens.


### 1. Why the Static System Prompt Injects on Every Loop

The token accumulation occurs because the standard **Azure Functions Agents `/chat` runtime** (and ReAct frameworks in general) treats tool calling as a conversational back-and-forth:

1. **Repetitive Tool Injections:** On every single turn, the runtime re-serializes the entire agent markdown file (`.agent.md`) plus the OpenAPI/JSON-RPC schemas for all registered tools.


2. **Context Compounding:** When an agent runs through `read` $\to$ `reason` $\to$ `commit`, the runtime re-submits the initial system instructions, tool definitions, and prior step history on every intermediate model call.


3. **The Built-in Framework Overhead:** The framework wraps system text with safety disclaimers, chat roles, and conversational schema formatting that consume 1,500–2,000 baseline tokens before the model sees a single weight.

### 2. Method 1: The Zero-Schema Bypassing Pattern (Durable Orchestration)

To avoid paying for the static system prompt and tool definitions on every iteration, you can **bypass the `/chat` agent harness entirely** using the **Durable Functions Orchestrator**.

Instead of treating the LLM as a tool-calling chat bot that needs JSON schemas, treat it as a **stateless numerical function predictor** inside a Durable Activity task:

```
┌────────────────────────────────────────────────────────────────────────┐
│ Durable Functions Orchestrator (loop_optimizer.py)[cite: 1]           │
│                                                                        │
│  while (iteration < MAX_TRIALS && loss > TARGET_LOSS):                 │
│    │                                                                   │
│    ├── 1. Activity: C++ reads Azurite directly[cite: 1]               │
│    │      (Downloads SJC1 binary, outputs TOTR string + loss)[cite: 1]│
│    │                                                                   │
│    ├── 2. Activity: Direct LLM Completion[cite: 1]                    │
│    │      • NO Tool Schemas (tools=None)[cite: 15]                    │
│    │      • NO Conversational Agent Envelope[cite: 1, 15]             │
│    │      • NO Chat History[cite: 1, 15]                              │
│    │      • Prompt: 80 tokens (Journal history + active TOTR)          │
│    │      • Output: 40 tokens (New TOTR string)                        │
│    │                                                                   │
│    └── 3. Activity: C++ commits and gates Azurite update[cite: 1]     │
│           (Returns {loss, status} to the orchestrator)[cite: 1]       │
└────────────────────────────────────────────────────────────────────────┘

```

#### The Activity Implementation (`orchestrators/loop_optimizer.py`)

In the LLM activity, invoke `client.chat.completions.create` directly with `tools=None` and `response_format={"type": "json_object"}`:

```python
@bp.activity_trigger(input_name="payload")
def activity_llm_synthesize(payload: dict):
    from openai import AzureOpenAI
    import os, json

    client = AzureOpenAI(
        api_key=os.environ["AZURE_OPENAI_API_KEY"],
        api_version="2024-02-01",
        azure_endpoint=os.environ["AZURE_OPENAI_ENDPOINT"]
    )

    # Completely stripped prompt: ~90 tokens total, ZERO tools attached
    minimal_prompt = f"""Task: Predict new TOTR weights to reduce loss.
History:
{payload['history_summary']}
Current Best: loss={payload['loss']:.4f}, max_res={payload['max_residual']:.4f}
Active:
l1_w: "{payload['l1_w']}"
l2_w: "{payload['l2_w']}"
l1_b: "{payload['l1_b']}"
l2_b: "{payload['l2_b']}"

Rules:
- Keep gamma in [0.02, 0.12]. Keep vector ints in [-30, 30].
- Perturb active vectors to push loss lower.
Emit strictly JSON: {{"l1_w":"...", "l2_w":"...", "l1_b":"...", "l2_b":"..."}}"""

    response = client.chat.completions.create(
        model=os.environ.get("AZURE_OPENAI_DEPLOYMENT", "gpt-5-mini"),
        messages=[{"role": "user", "content": minimal_prompt}],
        response_format={"type": "json_object"},
        temperature=0.3
    )
    return json.loads(response.choices[0].message.content)

```

**Token Savings:**

* Old `/chat` Turn: System Prompt (1,200) + Tool Schemas (850) + Context (500) = **~2,550 tokens per step**.
* Direct Activity Turn: Minimal Prompt (90) + Response (45) = **~135 tokens per step** (a 94% reduction).

### 4. Method 3: Prompt Caching (Prefix Optimization)

In Azure OpenAI and OpenAI deployments, **automatic prompt caching** activates when the prefix of the prompt exceeds 1,024 tokens and remains identical across requests.

To optimize caching when using the agent loop:

1. **Never inject dynamic data into the system prompt:** Keep the system prompt 100% static so it hits the cache across turns.
2. **Push rolling history into the user message:** Place dynamic values (`current_loss`, `history`, `active_tokens`) strictly at the tail of the payload:
```json
{
  "prompt": "Evaluate checkpoint sliding_totr.json. Current best loss is 0.5913. Propose update."
}

```


3. When cached, prompt tokens are billed at a **50% to 80% discount**, reducing cost even when the framework re-submits the wrapper.

### Recommendation

For true autonomous multi-trial loops, **Method 1 (Durable Activity Completion)** provides the highest efficiency:

* Tool schemas and static system envelopes are completely eliminated from the prompt.


* The LLM prompt scales with the data it consumes (~90 tokens of TOTR vectors and journal summaries).
* The orchestrator manages loop sequencing and termination, while C++ gates Azurite checkpoints on local loopback sockets.
